# Power BI Build Guide

This folder contains a Power BI-ready star schema and the DAX measures for the model. The `.pbix` itself is built in Power BI Desktop by following the steps below.

The `.pbix` is built locally in Power BI Desktop from the CSVs and DAX in this folder. The binary is not committed; the model definition is.

---

## Files in this folder

| File | Rows | Role in the model |
|---|---|---|
| `fct_leads.csv` | 534 | Fact table, one row per unique lead |
| `dim_campaign.csv` | 13 | Campaign dimension: advertiser, vertical, channel, contracted rates |
| `dim_date.csv` | 31 | Contiguous date dimension, required for time intelligence |
| `dim_state.csv` | 12 | Geography dimension with region rollup |
| `measures.dax` | 25 measures | Copy into a dedicated `_Measures` table |

All four tables are generated by `sql/03_export_powerbi.sql`. Re-running the SQL regenerates them, so the Power BI model refreshes from a reproducible pipeline rather than from hand-edited spreadsheets.

---

## Step 1: Load the data

`Home > Get Data > Text/CSV`, once per file. In the preview window use **Transform Data** rather than Load, and check the following in Power Query before applying:

- `fct_leads[lead_date]` is typed as **Date**, not Text. This is the most common cause of broken time intelligence.
- `fct_leads[acquisition_cost]` and `[commission_revenue]` are **Decimal Number**.
- `fct_leads[is_converted]` is **Whole Number** (it is a 0/1 additive flag, so it should sum).
- `fct_leads[is_cost_imputed]` is **True/False**.
- `dim_date[date_key]` is **Date**.

## Step 2: Build the relationships

In **Model view**, create four relationships. All are one-to-many, single filter direction, from the dimension to the fact:

| From | To | Cardinality | Direction |
|---|---|---|---|
| `dim_campaign[campaign_id]` | `fct_leads[campaign_id]` | 1 to many | Single |
| `dim_date[date_key]` | `fct_leads[lead_date]` | 1 to many | Single |
| `dim_state[state_code]` | `fct_leads[state_code]` | 1 to many | Single |

Leave every relationship **single-direction**. Bidirectional filtering is occasionally necessary but it creates ambiguity as a model grows, and nothing in this model needs it.

## Step 3: Mark the date table

Select `dim_date`, then `Table tools > Mark as date table`, and choose `date_key`.

Skipping this step is the single most common Power BI modelling error. Without it, `DATEADD` and every other time intelligence function will return results that look plausible and are wrong.

## Step 4: Create the measures

1. `Home > Enter Data`, name the table `_Measures`, click Load. It will contain one empty column.
2. Create each measure from `measures.dax` via `Modeling > New Measure`.
3. Once the first measure exists, right-click the placeholder `Column1` and hide it.
4. Set formats in the `Measure tools` ribbon: currency for cost and revenue measures, percentage with one decimal for rate and ROI measures.

Build the base measures first (`Total Leads`, `Conversions`, `Total Cost`, `Total Revenue`), since everything else references them.

## Step 5: Build the report pages

### Page 1: Executive Summary

- **Cards** across the top: `Total Leads`, `Conversions`, `Conversion Rate`, `Total Cost`, `Total Revenue`, `CPA`, `ROI`
- **Card** bound to `Headline Summary` for a written one-line position statement
- **Clustered bar chart**: `dim_campaign[channel]` on axis, `Efficiency Index` on values, sorted descending. Add a constant line at 1.0. Everything below the line is consuming more budget share than the conversion share it returns, which makes the Display problem visible without a table.
- **Line chart**: `dim_date[date_key]` on axis, `Net Contribution Running Total` on values. Shows cumulative margin burn across the month.
- **Slicers**: `dim_campaign[vertical]`, `dim_campaign[channel]`, `dim_date[week_label]`

### Page 2: Advertiser Detail

- **Table** with `dim_campaign[advertiser]` and the columns `Total Leads`, `Conversions`, `Conversion Rate`, `Conversion Rate CI Lower`, `Conversion Rate CI Upper`, `Evidence Strength`, `CPA`, `ROI`
- Apply conditional formatting to `Evidence Strength`: red for "Insufficient sample", amber for "Directional", green for "Actionable"
- **Scatter chart**: `CPA` on X, `Conversion Rate` on Y, `Total Cost` as bubble size, `dim_campaign[advertiser]` as legend. Underperformers separate into the lower-right quadrant.

The confidence columns are the point of this page. They are what stops a reader concluding that a 3.6% conversion rate on 28 leads is a finding.

### Page 3: Geography

- **Map** or filled map on `dim_state[state_code]`, `CPA` as the bubble size or colour saturation
- **Bar chart** by `dim_state[region]`

## Verification before you publish

Cross-check these against `sql/02_performance_analysis.sql` output. Any mismatch means a relationship or filter direction is wrong.

| Measure | Expected, no filters |
|---|---|
| Total Leads | 534 |
| Conversions | 67 |
| Conversion Rate | 12.5% |
| Total Cost | $12,835.30 |
| Total Revenue | $8,793.00 |
| CPA | $191.57 |
| ROI | -31.5% |
| Efficiency Index, Affiliate | 2.04 |
| Efficiency Index, Display | 0.48 |

Then filter to a single advertiser and confirm the numbers still reconcile to the SQL output at that grain. Totals matching while segments disagree is the classic signature of a bad relationship direction.

## Design notes

- **Why a star schema rather than the flat table the Excel version used?** Conforming dimensions let one measure slice consistently across advertiser, date, and geography without duplicating logic or resorting to bidirectional filters.
- **Why `DIVIDE` instead of `/`?** It returns blank rather than an error on a zero denominator, so a slicer selection with no conversions renders an empty card instead of breaking the page.
- **Why `ALLSELECTED` in the share-of-total measures rather than `ALL`?** `ALL` would compute share against the entire dataset and ignore page slicers, so the column would not total to 100% within the visual.
- **Why is `Evidence Strength` based on conversion count rather than interval width?** A segment with one conversion produces a narrow interval simply because the rate sits near zero. Width alone would classify it as well-measured when it is not.
